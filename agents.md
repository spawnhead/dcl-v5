Миграция Legacy Java ERM -> Современный стек (единственный целевой вариант)

## 0) Роль и цель агента
Ты - автономный инженер-мигратор. Твоя задача - переписать legacy ERM-приложение с сохранением бизнес-логики 1:1, но на современном стеке и архитектуре.
Ключевое требование - функциональный паритет. Любая реализованная фича должна быть трассируема до конкретного legacy-источника (Action/DAO/JSP/SQL).

## 1) Источники истины в репозитории (важно)
1) Legacy исходники находятся в папке `src/`
2) DDL схемы находится в папке `db/` и называется:
   `db/Lintera_dcl-5_schema.ddl`
3) Никаких предположений о схеме БД "на глаз" - первичный источник истины только этот DDL.
4) Любые выводы о таблицах, полях, связях, триггерах, генераторах, процедурах - делай только после анализа этого файла.

## 2) Целевой стек (фиксировано, не обсуждается)
### Backend
- Java 21 LTS
- Spring Boot 3.5.x
- Spring Modulith (modular monolith)
- Spring Data JPA + Hibernate
- PostgreSQL (миграция с Firebird)
- Flyway migrations
- REST API + OpenAPI/Swagger
- Maven или Gradle (выбери один и придерживайся)

### Frontend
- React 19 + TypeScript
- Vite
- Ant Design
- AG Grid Community
- TanStack Query
- OpenAPI autogenerated client
- React Hook Form + Zod
- React Router

## 3) Жесткие правила исполнения
### 3.1 Безопасность и аккуратность
- Не изменяй legacy-код в `src/`, если нет крайней необходимости.
- Новую реализацию добавляй отдельными директориями.
- Любая миграция - через воспроизводимые шаги: код + тесты + документация.

### 3.2 Запуск команд
- Все команды выполняй в bash (не в PowerShell).
- Если нужно выполнить команды сборки/тестов - выполняй их и фиксируй результат в логах проекта.

### 3.3 Трассируемость
- Для каждой новой фичи обязателен "trace" до legacy:
  - какой Struts Action / Service / DAO / JSP это реализует
  - какая таблица/процедура/триггер участвует
  - какие бизнес-правила применяются
- Если бизнес-правило найдено - оно должно появиться:
  1) в доменной модели или application layer
  2) в unit/integration тесте
  3) в документации домена

## 4) Структура целевого репозитория (создай)
Оставь legacy как есть, добавь новые папки:

- `modern/backend/` - Spring Boot modulith
- `modern/ui/` - React SPA
- `docs/` - документация миграции, домены, API, план
- `ops/` - docker-compose, nginx, скрипты миграции данных

Пример:

## ФАЗА 1 - Инвентаризация legacy и извлечение бизнес-логики
Цель - получить документированную доменную модель и карту функционала.

### 1.1 Проанализируй БД по DDL (db/Lintera_dcl-5_schema.ddl)
Сделай файл:
- `docs/DB_SCHEMA_SUMMARY.md`

В нем обязаны быть:
1) Список объектов:
- таблицы
- PK/FK/уникальные ограничения
- индексы
- генераторы/sequence (Firebird generators)
- триггеры
- views
- процедуры/функции
2) Таблицы по доменам (кандидатные bounded contexts)
3) Особые места Firebird, требующие миграции логики:
- триггеры, которые реализуют бизнес-правила
- генераторы, автоинкременты
- процедуры, которые используются приложением
- computed поля или нестандартные типы

Отдельно создай:
- `docs/DB_FIREBIRD_TO_POSTGRES_MAPPING.md`
Там опиши:
- маппинг типов (Firebird -> Postgres)
- как переносить генераторы (sequence + identity)
- как переносить триггеры (PL/pgSQL)
- как переносить процедуры (functions/procedures в Postgres)
- что будет перенесено как "логика приложения", а что как "логика БД"

Важно: если в legacy реально используются процедуры/триггеры как бизнес-логика, не теряй это - перенеси либо в Postgres (через миграции), либо в доменный слой. Выбор фиксируй в документации с аргументацией.

### 1.2 Проанализируй legacy Java (src/)
Сделай файлы:
- `docs/LEGACY_CODEMAP.md` - карта пакетов, подсистем, точек входа
- `docs/DOMAIN_ANALYSIS.md` - домены, агрегаты, правила, события
- `docs/FEATURE_INVENTORY.md` - список экранов/фич/операций

Что извлекать из legacy:
1) Struts Actions - как use cases
2) DAO/Service - как бизнес-операции и транзакции
3) JSP/Tiles - какие данные нужны UI, какие формы/валидации
4) SQL/JDBC/Hibernate - какие таблицы реально используются, какие запросы критичны

Для каждого домена обязательно:
- Aggregate Roots
- Value Objects
- Статусы и state machine
- Валидации
- Побочные эффекты (email, логирование, уведомления)
- Внешние зависимости между доменами

## ФАЗА 2 - Скелет modern backend (Spring Boot + Modulith + Postgres)
Цель - поднять "пустой" modulith, чтобы можно было делать вертикальные срезы.

### 2.1 Создай `modern/backend/`
Требования:
- Java 21
- Spring Boot 3.5.x
- Spring Modulith
- Spring Data JPA
- Flyway
- OpenAPI UI
- Validation
- Testcontainers для integration tests

Сразу добавь:
- базовую структуру модулей (папки доменов)
- `common/` (shared kernel) только для реально общих типов

### 2.2 База данных: Postgres + Flyway
Создай миграции Flyway в:
- `modern/backend/src/main/resources/db/migration/`

Правило:
- Миграции строятся на основе `db/Lintera_dcl-5_schema.ddl` (Firebird), но конечный результат - Postgres DDL.
- Таблицы/ограничения/индексы должны соответствовать смыслу legacy.
- Любая логика, которая была в Firebird триггерах/процедурах и важна для бизнес-правил - должна быть перенесена и покрыта тестами.

Добавь docker-compose для локального запуска Postgres:
- `ops/docker-compose.yml`

## ФАЗА 3 - Вертикальный срез 1 (один домен end-to-end)
Цель - первая полностью рабочая фича: БД + backend API + UI экран.

### 3.1 Выбор домена
Выбери домен с минимальными зависимостями (по итогам `FEATURE_INVENTORY.md` и `DB_SCHEMA_SUMMARY.md`).
Не выдумывай домены - базируйся на реальных таблицах и Actions.

### 3.2 Реализация домена по шаблону Modulith
В каждом модуле:
- `api/` - REST контроллеры + DTO
- `application/` - use cases
- `domain/` - агрегаты, правила, доменные события
- `infrastructure/` - JPA репозитории, адаптеры

Правила изоляции:
- доступ между модулями только через `api/` или доменные события
- прямые вызовы domain/application другого модуля запрещены

### 3.3 Тесты
Обязательны:
- unit tests на доменную логику
- integration tests на репозитории и транзакции (Testcontainers + Postgres)
- минимум один контрактный тест на API (проверка JSON shape)

## ФАЗА 4 - Modern UI (React)

## ФАЗА 5 - Миграция данных (Firebird -> Postgres)

Правила:
- порядок миграции таблиц должен учитывать FK
- после миграции должны быть проверки целостности (row counts, FK violations, spot checks ключевых таблиц)

4) Есть UI экран
5) Есть тесты, которые проверяют бизнес-правила

## 7) Контроль качества (обязательные гейты)

- Нет нарушений границ Modulith (используй проверку modulith)
- API latency целевое: p95 < 200ms для типичных запросов (фиксируй базовую метрику после появления первых реальных endpoint)
